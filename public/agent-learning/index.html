How the loop works

The agent's job is to read every module in the library and flag anything that has gone stale or wrong. This is how it gets better at that job over time. The cycle below runs once per module, and what it learns carries forward to the next one.

First, the starting point — before any learning happens
The library
Thousands of Microsoft Learn modules, each full of factual claims that can drift out of date.
The agent
Reads a module and flags claims that are no longer accurate — with how serious it is, and a suggested fix.
The goal
Make that flagging more accurate over time — without anyone editing the agent's code.
1

Give the agent its memory

Before it reviews a module, we hand it everything it has learned from past reviews — a running set of notes. On the very first run this memory is empty; each run after, it's a little fuller. The agent keeps these notes in mind as it works.

REAL · validation agent (gpt-5.4)
2

It reviews the module, claim by claim

For each claim it decides: still accurate, inaccurate, or can't tell — and how serious. This is the step its memory changes — the same claim can now get a different, better call because of a rule it learned earlier.

produces: rating · severity  ⟵ memory applied here
3

A content expert reacts

A human looks at what the agent flagged and responds: accept the fix, correct the call, or call it a false alarm. Each response becomes a "signal" — in effect a thumbs-up or thumbs-down on that one call. The signals are what the agent learns from.

SIMULATED reviewer
4

We score each signal against our goals

Every signal (not just one reaction — each call gets its own) is scored against what we want the agent to be good at: catch real problems, rate severity right, don't miss things. That score decides how much to adjust the agent's memory.

each signal → goal score
5

It writes the lesson into memory

When the same kind of correction keeps coming up, it becomes a new note ("rule") in memory — filed by how widely it applies. That memory is exactly what gets loaded back at step 1 for the next module.

saved as: a scoped rule
↺  The next module is reviewed with the now-smarter memory — and the cycle repeats. No one edited the agent's code.

What drove the change — the actual lessons the agent wrote for itself

These are the real procedural-memory rules the agent created from the reviewer feedback — the exact wording it now follows. Each is filed by how broadly it applies: task one topic · group a product area · global everywhere. That tag is the "level" the agent learned at. This exact text is what gets injected into its prompt next time (see the prompt appendix at the bottom).

Is the 100% "real"? Partly an artifact of the demo, and worth being upfront about: because the simulated reviewers follow fixed rules, once the agent learns those rules it can match them exactly — so the ceiling here is artificially clean. With live reviewers the number would land lower and be noisier. The point isn't the 100% — it's that the gap closed on its own, by the agent learning from feedback, with nobody rewriting its instructions. That mechanism is the real thing.
"Doesn't this need a huge amount of data?" No — and this is the key difference from model training. This is not fine-tuning (which needs thousands of examples to nudge a model's weights). It works more like a person making a mistake and remembering it: one clear correction becomes a rule the agent applies on the very next similar claim. So the learning shows up in a handful of interactions, not thousands.
Why it keeps working as the world changes. Two things: (1) Lessons are weighted, not absolute. A new lesson doesn't land as 100% truth — it carries a confidence weight that rises or falls as more evidence comes in, so the lessons that keep proving useful float to the top and weak ones fade. (2) It self-corrects for drift (the technical term is concept drift): the real-world problem where what's true today goes stale tomorrow, which silently degrades almost every generative-AI system over time. Because those weights keep re-adjusting to new feedback, lessons that stop being helpful lose weight and get replaced on their own — the agent adapts to the changing world instead of decaying with it. Drift goes from a constant liability to something the system absorbs. That's a major advantage of this design.

Goals & the optimization loop

The goals are the specific outcomes we want the agent to get better at. There are three. Each has a weight (set by the client) that says how much it matters. Every signal from steps 3–4 is scored against the goal it affects, and the weighted blend of the three is the single target the agent tunes its memory toward. Change the weights, and you change what the agent optimizes for.

The goal scores here are ⚠ PLACEHOLDER (from the simulated signal). The goals, the weights, and the mechanism below are real.

How a goal is actually applied — the optimization process

Two parts work together: an LLM that writes the lessons, and a formula that weights them over time.

① Writing the lesson — an LLM does this
When the reviewer corrects the agent, a model reads the correction, the current rules, and the weighted goals, and writes or refines one general, plain-language rule aimed at improving those goals. This is the "verbal" learning — the same idea as LangMem's prompt/rule optimizer.
② Weighting the lessons — a formula does this
Each rule then carries a running-average weight a simple formula nudges every time the rule succeeds or fails: 0.50→0.60→0.68 when it keeps getting accepted, 0.50→0.40→0.32 when rejected. Best lessons float to the top, stale ones fade — fast, cheap, auditable, and how drift is handled.

Where the goal + its weight enter: each signal is scored against the goal it affects (accepted flag → precision; severity match → severity; real issue kept → coverage), then weighted by who gave it and by the goal's client-set weight — so the goals you care about steer both what the LLM writes and which rules the formula floats to the top. Behavior shifts toward your goals with no one editing the agent's code.

What the agent remembers — three kinds of memory ⚠ ILLUSTRATIVE

When a reviewer corrects something, the agent doesn't just store "the answer." It records three kinds of memory (the CoALA model), each doing a different job — and it starts with seed memory so it isn't empty on day one.

Seed memory — procedural memory, loaded before any learning

These are procedural rules (the "how to judge" heuristics) lifted from the agent's existing rubric and loaded on day one, so it starts like an experienced reviewer instead of blank. Seeds compete on the same footing as learned rules — a seed that keeps failing loses weight and fades too.

One correction → three memories extracted (example: a reviewer confirms "Azure AD" is now "Microsoft Entra ID")
Episodic — what happened, once
"On this module, the agent flagged an 'Azure AD' claim; the reviewer accepted the fix to 'Microsoft Entra ID'." The specific situation + how it turned out — reused as a worked example next time something similar shows up.
Semantic — a durable fact
"Azure AD → renamed to → Microsoft Entra ID." A reusable fact, true until it changes — so the agent doesn't have to re-research it every time.
Procedural — a reusable rule (before → after)
Before: no rule for renamed products. After: a new rule — "flag the old product name and suggest the current one" — that the agent applies to the next rename it sees.

Procedural memory is where learning shows up in behavior. A brand-new pattern adds a new rule; a recurring correction reinforces an existing one (its weight goes up). Both happen — that's the section below.

The agent's memory — one memory, filed by how broadly each lesson applies ⚠ PLACEHOLDER DATA

It's one memory, not four separate ones. Every lesson sits somewhere on a single scale of breadth — from one reviewer's preference up to a corpus-wide rule. The level just sets how far a lesson reaches and how much weight it gets when the agent pulls up memory.

Appendix — the agent's prompt, before & after memory

The core idea. A prompt is procedural memory — a set of "how to do the job" rules — it's just frozen. (That's why people often call a prompt procedural memory; the catch is the rules never change.) This whole effort is to un-freeze it: we load the existing prompt's rules as the agent's starting memory, then let reviewer feedback adjust them. So we pulled all the judgment rules out of the prompt and made them learnable.

The prompt is just stable operating scaffolding (role, grounding tools, what the rating/severity labels mean, output format) plus one JUDGMENT RULES section. There is no permanent rubric. How the agent judges a claim lives entirely in that memory — which starts as the team's existing rubric, loaded as seed rules, and then changes as the agent learns. So the rubric isn't a fixed law baked into the prompt; it's the starting point the agent improves on (a seed rule can be re-weighted or overruled by a higher-reliability learned rule).
